# Subgraphs

One TypeScript file, and you get a table plus a REST API over it. You don't pick the API shape; if you need your own, use [Index](/docs/index).

<Yields page="subgraphs" />

## Define a subgraph

A subgraph [names its sources](focus:sources), [declares a table](focus:schema), and [writes one handler per source](focus:handlers). The [first run backfills from startBlock](hover:start); new blocks stream in after. This one reads a pool's reserves map, so anyone can rebuild its rows.

```ts subgraphs/pool-reserves.ts figure
import { defineSubgraph } from "@secondlayer/subgraphs";

export default defineSubgraph({
  name: "pool-reserves",
  // !ref[/startBlock/] start
  startBlock: 1230000,
  // !ref(1:7) sources
  sources: {
    reserves: {
      // !callout[/map_set/] State writes only, so the rows can be recomputed.
      type: "map_set",
      contractId: "SP102V8P0F7JX67ARQ77WEA3D3CFB5XW39REDT0AM.amm-vault-v2-01",
      map: "reserve",
    },
  },
  // !ref(1:6) schema
  schema: {
    reserves: {
      columns: { token: { type: "principal" }, balance: { type: "uint" } },
      uniqueKeys: [["token"]],
    },
  },
  // !ref(1:5) handlers
  handlers: {
    reserves: (event, ctx) => {
      // !callout[/upsert/] Same input, same row, on every run.
      ctx.upsert("reserves", { token: event.key as string }, { balance: event.value as bigint });
    },
  },
});
```

Accumulating a value, reading contract state, and typing a `print` payload each have a rule worth knowing: [Handlers](#handlers).

## Deploy

Hosted is the default path: one private stack per account, no box to run. Create an `sk-sl_*` key at [`/account/keys`](/account/keys), set the two variables from the [Introduction](/docs#get-started), and deploy (CLI 19.1 or later). The first deploy backfills from `startBlock`; new blocks stream in after.

```text ~/pool-reserves
$ secondlayer subgraphs deploy subgraphs/pool-reserves.ts
✓ Subgraph "pool-reserves" created → v1.0.0
# !mark
  verification  state · pin 7f3c…a91e
  unproven      tx attribution of writes: event.tx, _tx_id (needs event proofs)
```

Set a start block. Without one the subgraph reindexes from genesis, and every matching event and transaction row it reads bills ([what it costs](tip "The first 1M rows a month are free, then $5 per 1M rows. Block headers are always free.")). The `verification` line is the level your sources earn and `pin` hashes what you deployed: [Rows anyone can recompute](#rows-anyone-can-recompute).

## Handler context

Each handler gets `(event, ctx)`: `ctx.tx` / `ctx.block` for metadata, `ctx.insert` / `update` / `upsert` / `delete` / `increment` for writes, `ctx.findOne` / `findMany` to read rows back.

A `contract_call` source with a `functionName` types `event.input` from the contract's ABI. `secondlayer subgraphs deploy` fetches it from the deployed contract, so you don't paste it. Pass `abi` yourself for wildcard, multi-contract or trait sources, or a local deploy.

## Hoisting the schema

Pull `schema` out of the call with `defineSchema()` when a handler grows
enough to factor a helper, and the helper stays fully typed:

```ts
import { defineSchema, defineSubgraph, type TypedSubgraphContext } from "@secondlayer/subgraphs";

export const schema = defineSchema({
  balances: {
    columns: { holder: { type: "principal" }, amount: { type: "uint" } },
    uniqueKeys: [["holder"]],
  },
});

function credit(ctx: TypedSubgraphContext<typeof schema>, holder: string) {
  ctx.increment("balances", { holder }, { amount: 1n });
}

export default defineSubgraph({ name: "balances", schema, sources, handlers });
```

With only the definition in scope, `InferContext<typeof def>` gives the same typed `ctx`.

## Indexing a contract set

`contractId` takes an array, so a router plus its pools is one source and one
handler instead of twelve of each:

```ts
sources: {
  swaps: { type: "print_event", contractId: [ROUTER, POOL_A, POOL_B], topic: "swap" },
}
```

For a set that **grows** (pools created after you deploy, launchpad-minted
tokens, registry entries), use a `factory`. It extracts addresses from
another source's events:

```ts
sources: {
  registry: { type: "print_event", contractId: REGISTRY, topic: "pool-created" },
  swaps: {
    type: "print_event",
    topic: "swap",
    factory: { from: "registry", field: "data.pool" },
  },
}
```

Two guarantees: a pool discovered in block N receives its **own** block-N
events (discovery runs before matching), and the discovered set is rolled
back on a reorg like any other chain-derived state, so an address announced on
an orphaned fork stops matching.

## Index by standard, not by address

`trait` resolves to **every contract Secondlayer classifies as that standard**, including ones deployed after you ship:

```ts
sources: {
  // every SIP-010 token transfer on-chain
  tokens: { type: "ft_transfer", trait: "sip-010" },
},
```

Traits: `sip-009`, `sip-010`, `sip-013`. A reindex backfills each contract from its deploy block and bills the rows it reads. [Find contracts by standard](/docs/index#find-contracts-by-standard) queries the set directly.

## Test before you deploy

```bash
secondlayer subgraphs test subgraphs/bns-names.ts --from 167484 --to 167600
secondlayer subgraphs test subgraphs/bns-names.ts --offline   # replay the cassette
```

Real chain events, your local handler code, no deploy. The first run records
a cassette so later runs are free and offline; changing a source filter
discards it rather than passing against data the subgraph would no longer
request. If events arrive and your handlers write nothing, the command fails,
which is the shape of a field-mapping bug that would otherwise ship a
0-row subgraph.

For unit tests, `@secondlayer/subgraphs/testing` gives you the same context
the runtime uses, backed by memory:

```ts
import { buildEvent, createTestContext } from "@secondlayer/subgraphs/testing";

const ctx = createTestContext(bns.schema, { block: { height: 167_484 } });
await bns.handlers.bns!(buildEvent(bns.sources.bns, { topic: "name-register", data }), ctx);
expect(await ctx.rows("names")).toMatchInlineSnapshot();
```

Handlers that read the chain get stubbed reads instead of a node, so pass
`reads: { "<contract>.<function-name>": value }` to `createTestContext`. An
unstubbed read throws naming the key it wanted.

## Handlers

A handler turns one matched event into rows. Accumulating a value, reading contract state, and typing a `print` payload each behave differently than they look.

### Counters and balances: use `increment`

`ctx.increment(table, key, deltas)` applies a **delta** in one atomic
statement (upserting the row on the table's `uniqueKeys`). Reach for it
whenever a value accumulates:

```ts
ctx.increment("balances", { holder }, { amount: -amount });
```

The tradeoff: a delta is applied once per pass over a block. Tip-first deploys
(`backfillMode: "concurrent"`) and `backfill` revisit blocks the live walk
already processed, so they refuse handlers that call `increment`, `update`,
`findOne` or `findMany`. Those subgraphs deploy with the default blocking
backfill and rebuild with `reindex`.

#### Why not read, compute, upsert

The read-modify-write it replaces (`findOne` → compute → `upsert`) looks
equivalent and isn't. Two events touching the same row in one block both read
the stale value and the second write wins, so updates are silently lost. Deltas
commute within a block, and a reorg rewind reverses them cleanly.

#### System columns

Every row carries `_block_height` and `_tx_id`: the block and transaction
that created it. An `upsert` or `increment` on an existing key changes your
columns (last write wins) and leaves these alone, whether the first write was
in an earlier block or earlier in the same one. A key deleted and written
again is a new row, so the new writer's block and transaction are stored.

#### Reading the chain from a handler

Some facts aren't in any event. A token's `decimals`, a pool's reserves, an
NFT's metadata URI: those live in contract state, and without them `amount` is
a bare integer nobody can render. `ctx.client` calls read-only functions for
you:

```ts
import { readContractAt } from "@secondlayer/subgraphs";

const SIP010 = { functions: [ /* get-decimals, get-symbol … */ ] } as const;

handlers: {
  transfer: async (event, ctx) => {
    const token = readContractAt(ctx, contractId, SIP010, {
      cache: "contract-constant",
    });
    const decimals = await token.read.getDecimals({}); // bigint — typed from the ABI
  },
},
```

Same shape as [`getContract`](https://stacks.secondlayer.tools/guide/transactions), minus `call`: a handler indexes the
chain, it never writes to it.

**Every read is pinned to the block being processed.** The call carries that
block's `index_block_hash`, so reprocessing the same blocks produces
byte-identical rows. A block whose id was never persisted **throws** rather
than falling back to the node's tip, which would make the same reindex return
different values.

<Callout type="tip" title="Declare what can't change">

Results are cached in Postgres, keyed by block, which dedupes reads across
events but still costs one call per block. For values that genuinely cannot
change, pass `cache: "contract-constant"` and it is fetched **once**, ever.
That is what makes a full backfill affordable. Declaring it on a value that
does change pins the first answer forever, so it is opt-in and never inferred.

</Callout>

Self-hosting: set `STACKS_NODE_RPC_URL` on the subgraph processor, pointing at
the node you already run rather than a new service. See
[self-host](/docs/self-host#config).

#### Typed print payloads

Clarity ABIs don't describe `print` payloads, so `event.data` is untyped. A `prints` map types it, discriminated on `event.topic`:

```ts
sources: {
  registry: {
    type: "print_event",
    contractId: "SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-registry",
    topic: "completed-deposit",
    prints: {
      "completed-deposit": { bitcoinTxid: "text", amount: "uint" },
    },
  },
},
handlers: {
  registry: (event, ctx) => {
    event.data.bitcoinTxid; // string — typed, no casting
    event.data.amount;      // bigint
  },
},
```

<Callout type="warning" title="Don't guess print fields">

Payload shape varies per topic, and a guessed field silently nulls forever. Scaffold from the contract's **observed** history instead.

</Callout>

```bash
secondlayer subgraphs create sbtc-registry \
  --from-contract SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-registry
```

Scaffolds from the [print-schema endpoint](tip "Returns each print topic's payload shape for one contract, sampled from indexed prints."): one `print_event` source per topic with its `prints` map, plus one wide table (`--table-per-topic` splits it per topic). `secondlayer codegen prints <file>` emits a `.d.ts` of the payload types.

Deploys return advisory `warnings` when a handler reads an `event.data` field never observed for its topic (pinned `contractId` sources only). If the source **declares** a `prints` map, the same finding is an error and the deploy is refused: you stated the shape, so a mismatch is a defect rather than a hint.

#### Rows anyone can recompute

A subgraph whose sources are all state writes (`var_set`, `map_set`, `map_delete`) can be rebuilt from block headers alone, so its handlers must give the same rows on every run. The level is derived from your sources and a scan of the bundle, never configured:

| `verification.level` | Sources | Handler findings |
| --- | --- | --- |
| `state` | state writes only | refuse the deploy: `422 NONDETERMINISTIC_HANDLER`, each as `file:line:column` |
| `events` | events, prints, contract calls, `map_insert`, or any `ctx.client` read | advice in `verification.reasons`; deploys as before |
| `none` | `trait` scope, or `backfillMode: "concurrent"` | advice, as above |

| Refused at `state` | Use instead |
| --- | --- |
| `Date`, `performance`, timers, `fetch`, `process`, `crypto`, `Intl`, `toLocaleString` | values from `event`, `ctx.block`, `ctx.tx` |
| `Math.random`, `Math.sin` and other approximated `Math` | `bigint` math; `Math.abs/min/max/floor/ceil/trunc/sign/round` |
| non-integer or unsafe `number` in a row | `bigint` |
| `findOne` calls in parallel (`Promise.all`) | `await` each read in turn |

Verifiable handlers run in a locked-down realm that throws on the same list at runtime and retries the block rather than skip the event. The tradeoff: most event subgraphs stay advisory until event proofs ship. `pin` hashes the schema, bundle, `startBlock`, network and runtime version, so a handler-only redeploy changes it even when `schemaHash` does not.

A `state` subgraph reads its writes from the node's `state_writes` once the instance holds them from its `startBlock` on, and from `vm_events` until then. Nothing to configure.

#### Check rows

Recompute a `state` subgraph and compare it with the served rows, as in [Check it](#check-it). Each link proves:

| Link | Proves |
| --- | --- |
| `pin` | the served bundle, schema and `startBlock` are the ones the pin hashes |
| `blocks` | every block in the range, from the checkpoint |
| `txs` | each block's transactions hash to its header's tx merkle root |
| `inputs` | each block's writes are named in full, nothing hidden |
| `handlers` | the bundle runs in the deterministic realm over those writes |
| `rows` | served rows equal the recomputed ones on declared columns and `_block_height` |

`_tx_id` is not compared: which transaction made a write is unproven, as are writes overwritten within one block. A `--from` after `startBlock` is inconclusive (exit `2`) once a handler reads or merges earlier rows (`findOne`, `increment`, a partial upsert). Every read is free: proofs and state writes from `/v1/proofs/writes`, rows from `/v1/subgraphs`. Witnesses are limited to 2 per second, so 1,000 blocks take 8 minutes or more. An instance whose node does not deliver `state_writes` cannot be checked: exit `2`.

## Tip-first deploys

`--tip-first` (or `backfillMode: "concurrent"`) goes live at the tip, so rows are queryable in seconds while history backfills. The history fill revisits blocks, so it only takes handlers that write with `insert` or a full-row `upsert`. A handler that calls `update`, `increment`, `findOne` or `findMany` is refused with `TIP_FIRST_NON_REPLAYABLE_HANDLER`; deploy it with the default blocking backfill. The same rule applies to `secondlayer subgraphs backfill`: use `reindex` for a clean rebuild instead.

## What runs hosted

| | Hosted |
| --- | --- |
| Sources | Event filters (`stx_*`, `ft_*`, `nft_*`, `print_event`, `nested_contract_call`, `var_set`, `map_*`), `contract_call`, `contract_deploy`. Anything else: `422 SOURCE_NOT_HOSTABLE`, naming the source |
| Isolation | Handlers run in a gVisor sandbox with 512 MB, reaching only Secondlayer's API and the public internet |
| Visibility | Private. No public catalog, fork or marketplace |

A processor that stalls or runs out of memory is restarted. After 3 deaths at the same height the subgraph is marked `error`: fix the handler and redeploy. On your own box any source runs: [Self-host](/docs/self-host#what-differs-on-your-box).

## Read rows

A deployed subgraph serves its tables three ways: paged REST, a live stream, and a typed ORM schema over the same Postgres (the last is self-host only).

### Pages, cursors, and sorting

Pages are `_id`-keyset: `?cursor=<next_cursor>` resumes, `_order=asc|desc` sets direction. Sort by one column instead with `?_sort=<column>&_order=asc|desc`, and the cursor pairs that column with `_id` as a tiebreaker, so pages stay stable even when values tie.

```bash
# top holders by amount, paginated
curl "$SECONDLAYER_API_URL/v1/subgraphs/asset-holdings/holdings" \
  -H "Authorization: Bearer $SECONDLAYER_API_KEY" \
  -G -d "_limit=5" -d "_sort=amount" -d "_order=desc"
```

#### Read your table

Typed from the SDK (`new SecondLayer()` reads `SECONDLAYER_API_URL` and `SECONDLAYER_API_KEY`), or REST at `/v1/subgraphs` with wildcard CORS.

#### Cursor and sort rules

The cursor's shape follows the sort: don't hand-construct a sorted cursor, and replaying it under a different `_sort`/`_order` is a `400`. Multi-column `_sort=a,b`, `jsonb` columns and `_offset` are also `400`, since deep `OFFSET` scans hurt on big tables. `_limit`, `_fields`, `_search` and column filters work as everywhere else: [REST API](/docs/rest-api).

#### Indexed and searchable columns

Mark a column `indexed: true` if you plan to sort on it. Sorted reads get a `(column, _id)` index that matches the page order, so deep pages stay flat. Existing tables pick it up on their next reindex or schema change. `_search` needs at least one column marked `search: true`; on a table with none it is a `400` rather than matching everything.

#### Open reads

Reads send `Authorization: Bearer $SECONDLAYER_API_KEY`, with wildcard CORS, the same as `/v1/index` and `/v1/streams`. There is no per-subgraph visibility flag: hosted subgraphs are private to your account, and on your own box who can reach the instance is what your publish spec and reverse proxy decide ([Instance token](tip "The hex token your own box requires for reads past loopback and for every write.")). Every route and parameter (rows, `/count`, `/aggregate`, `/:id`, `/stream`): [API reference](/docs/api/subgraphs#list-subgraph-rows). Aggregate grammar: [aggregates](/docs/rest-api#aggregates).

#### Stream rows in real time

Tail a table over Server-Sent Events from the tip, or `?since=<block_height>` to replay a height then tail live. Column filters work as query params.

```bash
curl -N "$SECONDLAYER_API_URL/v1/subgraphs/sbtc-flows/transfers/stream" \
  -H "Authorization: Bearer $SECONDLAYER_API_KEY" \
  -G -d "since=8050000"
```

`subscribe` wraps it with the same `where` filters as `findMany` and returns an unsubscribe:

```ts
const unsubscribe = subgraph.transfers.subscribe(
  (row) => console.log(row),
  { where: { sender: "SP3PE7Q9...X44J" }, since: 8050000, onError: console.error },
);
```

It uses the global `EventSource`, so browser or **Node ≥ 22** only. Wire contract: [Streaming (SSE)](/docs/rest-api#streaming-sse).

#### React to your rows

Webhooks fire on chain events. To act when your subgraph writes a row, watch the table: it is your data.

**On your own box**

Your tables live in your instance's Postgres, in schema `subgraph_<name>` (dashes become underscores). A trigger tells your app the moment a block's rows commit:

```sql
CREATE OR REPLACE FUNCTION notify_sbtc_transfers() RETURNS trigger AS $$
BEGIN
  PERFORM pg_notify('sbtc_transfers', NEW._id::text);
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER sbtc_transfers_notify
  AFTER INSERT OR UPDATE ON subgraph_sbtc_flows.transfers
  FOR EACH ROW EXECUTE FUNCTION notify_sbtc_transfers();
```

```ts
import postgres from "postgres";

const sql = postgres(process.env.DATABASE_URL!); // your instance's Postgres

await sql.listen("sbtc_transfers", async (id) => {
  const [row] = await sql`SELECT * FROM subgraph_sbtc_flows.transfers WHERE _id = ${id}`;
  if (row) await handle(row);
});
```

- A notification goes out when the block commits, so you never act on a row that rolled back.
- Send `_id`, not the row: a payload is capped at 8,000 bytes.
- A notification sent while nothing listens is gone. On start, read rows past the last `_id` you handled, then listen.
- A reindex or a destructive redeploy rebuilds the schema and drops your trigger. Create it from the script that deploys.

**Hosted**

Hosted tables live in your account's private stack, so read them over the API. Poll and keep the last `next_cursor`:

```ts
let cursor = await loadCursor(); // last next_cursor saved, or undefined

for (;;) {
  const page = await sl.subgraphs.rows("sbtc-flows", "transfers", { cursor, order: "asc", limit: 100 });
  for (const row of page.rows) await handle(row);
  // !ref[/next_cursor/] next
  cursor = page.next_cursor ?? cursor;
  await saveCursor(cursor);
  if (page.rows.length < 100) await new Promise((resolve) => setTimeout(resolve, 5_000));
}
```

[`next_cursor`](hover:next) comes back on every page that has rows, and is `null` only on an empty page, so `cursor = page.next_cursor ?? cursor` keeps your place while nothing new arrives. A paging loop that reads a whole table ends on an empty or short page. A reorg rewrites the affected rows under new `_id`s: polling sees the new rows, not the removed ones, so wait until a row is a few blocks behind `tip` before you move money on it.

#### Typed ORM schemas (codegen)

Subgraph rows live in your instance's Postgres, so codegen needs direct database access and is self-host only. `codegen` emits a typed ORM schema for a subgraph's tables so your app reads them with Prisma, Drizzle, or Kysely:

```bash
secondlayer codegen subgraph ./subgraph.config.ts --target prisma -o prisma/schema.prisma
npx prisma generate
```

Generators: `--target prisma|drizzle|kysely`. Secondlayer owns the DDL, so treat the tables as read-only: verify with `prisma db pull`, never `migrate`.
