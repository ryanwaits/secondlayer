# Handle Stacks reorgs in your indexer

A reorg orphans blocks your tables already hold. Delete your rows from the fork height, inclusive, then read forward again. One key, one call to see them:

<CodeTabs sync="lang">

```bash
curl "$SECONDLAYER_API_URL/v1/streams/reorgs?since=2026-08-01T00:00:00Z&limit=1" \
  -H "Authorization: Bearer sk-sl_…"
```

```ts
import { SecondLayer } from "@secondlayer/sdk";

const sl = new SecondLayer({ apiKey: process.env.SECONDLAYER_API_KEY });

const page = await sl.streams.reorgs.list({
  since: "2026-08-01T00:00:00Z",
  limit: 1,
});
```

Keep rows from the orphaned range and your tables describe a chain that no longer exists.

## Pick the path you're on

How you read decides how much rollback code you write.

| You read with | What happens on a reorg | You do |
| --- | --- | --- |
| [A consumer](/docs/index#reorgs) | It rewinds and calls `onReorg` | Delete from the fork height |
| [A sink](/docs/sinks#rollback-is-height-stamped) | It deletes the rows and rereads | Nothing |
| [A subgraph](/docs/subgraphs) | Rows are rewritten under new ids | Wait a few blocks before moving money |
| [A webhook](/docs/webhooks#reorg-rollback) | `chain.reorg.rollback` lists what may have arrived | Undo each entry |

- Delivery after a rewind is at least once, so keep writes idempotent.
- The fork block itself is re-delivered, which is why the delete is inclusive.

## Skip reorgs entirely

Rows at or below `tip.finalized_height` never reorg, so a consumer that reads only those has nothing to undo. The tradeoff is freshness: `finalizedOnly` holds delivery until each row is final, which can put you hundreds of blocks behind the tip.

Use it for accounting and reports. Keep the rollback path for anything a user watches live. The option is on the [Index consumer](/docs/index#reorgs).
