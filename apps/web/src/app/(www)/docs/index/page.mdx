# Index

Decoded rows you sweep into your own tables. You write the loop; the decoding, the backfill, and the reorg rewind are done.

1M rows free a month hosted, [no meter on your own box](/docs/self-host#instance-token).

## Build your index on it

`consume()` is a checkpointed consumer with automatic reorg rewind: write rows in `onBatch`, return the cursor you committed, and a crash resumes from your checkpoint.

```ts
import { Index } from "@secondlayer/sdk";

const index = new Index();
await index.events.consume({
  eventType: "ft_transfer",
  fromCursor: await db.loadCheckpoint(), // null on first run
  fromHeight: 0, // first run: backfill from genesis
  onBatch: async (events, envelope, ctx) => {
    await db.transaction(async (tx) => {
      for (const t of events) await tx.upsertTransfer(t);
      await tx.saveCheckpoint(ctx.cursor); // commits with the rows
    });
    return ctx.cursor;
  },
  onReorg: (reorg) => db.deleteFromHeight(reorg.fork_point_height),
});
```

Where to run it: [Deploy](/docs/deploy). To have the loop run for you: [Subgraphs](/docs/subgraphs).

<details id="options">
<summary>Options</summary>

| Option | Effect |
| --- | --- |
| `eventType` | A literal narrows the rows: `"ft_transfer"` hands `onBatch` typed `amount`/`sender`, `"print"` hands it `payload.topic`. No discriminant check to write |
| `contractId` | One id, or an array to follow a whole protocol on one cursor: `["…sbtc-token", "…sbtc-registry"]`, up to 20. Mutually exclusive with `trait` |
| `txContext: true` | Joins the submitting tx into each event (`tx_sender`, `tx_type`, …). Same on `walk` and `list`; every row carries its submitting tx, so no per-event `/v1/index/transactions` call |
| `finalizedOnly: true` | Holds delivery to rows at or below `tip.finalized_height`; finalized data never reorgs, so `onReorg` is unnecessary |
| `signal` | Abort checked between batches, never mid-commit: the in-flight batch always commits; see [Deploy](/docs/deploy#handle-sigterm) |
| `index.contractCalls.consume()` | Same loop for decoded calls; already carries `sender`/`function_name`, so it needs no `txContext` |

</details>

<details id="reorgs">
<summary>Reorgs</summary>

Read envelopes carry a `reorgs` array: the reorganizations overlapping the page's height range, empty when none.

```json
{
  "reorgs": [
    {
      "id": "...",
      "detected_at": "2026-06-05T12:00:00Z",
      "fork_point_height": 892100,
      "old_index_block_hash": "0x…",
      "new_index_block_hash": "0x…",
      "orphaned_range": { "from": "892101:0", "to": "892140:7" },
      "new_canonical_tip": "892140:3"
    }
  ]
}
```

Roll back rows whose cursor falls inside `orphaned_range`, then re-fetch from `new_canonical_tip`. `consume()` does both for you.

In `onReorg`, the fork block and everything above it is no longer canonical, so delete rows at `fork_point_height` and above (inclusive); the consumer then rewinds the cursor and re-reads the canonical run for you.

Both bounds are `<block_height>:<event_index>` cursors tracking decoded-event positions. On transaction-keyed feeds (`/transactions`, `/contract-calls`), compare by the block-height component.

Running balances: invert them in a sink's `onRollback` ([Sinks](/docs/sinks#rollback-is-height-stamped)).

</details>

<details id="progress-and-health">
<summary>Progress and health</summary>

`ctx` carries where the sweep has reached, so liveness needs no bookkeeping of its own.

| Field | Is |
| --- | --- |
| `cursor` | The checkpoint to commit alongside your rows |
| `height` | Highest canonical block a row was DELIVERED from; event recency, parks on a quiet filter |
| `scannedHeight` | Highest block VERIFIED; an empty page proves nothing matches up to the tip; rolled back on a reorg |
| `tipHeight` | Chain tip as of this page's read |
| `blocksBehind` | `tipHeight - scannedHeight`, floored at `0`; real backlog, `~0` for a caught-up tail even when `height` is old |

Verify your mirror: check your tables against the canonical chain any time.

```ts
const { canonical } = await sl.index.canonical({ fromHeight: myLowestHeight });
for (const block of canonical) {
  if (myHashAt(block.block_height) !== block.block_hash) {
    await db.deleteFromHeight(block.block_height); // diverged — re-sweep from here
    break;
  }
}
```

To prove a block or transaction rather than compare hashes: [Verify](/docs/verification).

</details>

<details id="cost-and-history">
<summary>Cost and history</summary>

Reads on your own box hit your own Postgres: no meter, no rate limit. Hosted `api.secondlayer.tools` bills `rows.delivered` (1M free per account per month; rates and free block headers in [Keys and billing](/docs/authentication)). `from_height=0` reaches whatever history your instance holds; restoring more from the signed archive is metered ([archive credits](/docs/authentication#archive-credits)). Hosted is keyed; on your own box see [Self-host](/docs/self-host#instance-token).

</details>

## Other ways to read

One page with `list()`, a one-off export with `walk()`. Neither checkpoints, so neither is a live index.

<details id="list-walk-consume">
<summary>list, walk, consume</summary>

Every feed offers the same three verbs. They are not interchangeable.

```ts
const { rows, next_cursor } = await sl.index.blocks.list({ limit: 10 }); // one page
for await (const t of sl.index.ftTransfers.walk({ contractId })) {} // every row, once
await sl.index.events.consume({ eventType: "ft_transfer", onBatch }); // forever, resumable
```

| Verb | Gives you | Follows cursors | Checkpoints | Reorgs | Ends |
| --- | --- | --- | --- | --- | --- |
| `list()` | One page plus the envelope | No; you pass `cursor` back | No | Reports `reorgs[]`; you act | Immediately |
| `walk()` | An async iterable of rows | Yes, automatically | No | Ignored | On catching the tip |
| `consume()` | A loop calling your `onBatch` | Yes, automatically | Yes; you commit the cursor | Rewinds and fires `onReorg` | Never; tails until aborted |

`walk()` into a database is a trap. It works, and it's right for a one-shot export or an analysis script. As a live index it fails three ways: no checkpoint, so a crash restarts from zero; reorgs are ignored, so a fork leaves orphaned rows behind forever; and it returns at the tip instead of following the chain. Writing rows you intend to keep is `consume()`.

</details>

<details id="plain-http">
<summary>Plain HTTP</summary>

```bash
curl "$SECONDLAYER_API_URL/v1/index/events?event_type=stx_transfer&limit=20" \
  -H "Authorization: Bearer $SECONDLAYER_API_KEY"
```

Every endpoint, filter and response shape is in the [API reference](/docs/api-reference#list-events). `GET /v1/index` describes itself at runtime, so an agent can learn each `event_type` without docs.

On the events and contract-call feeds, `contract_id` takes a comma-separated set (max 20): one cursor over a protocol's contracts. `tx_context=true` puts `tx_sender`, `tx_type`, `tx_status`, `tx_contract_id` and `tx_function_name` on every event in one pass. For `print` events it is the only place the sender lives.

Every list response carries the collection, an opaque `next_cursor`, the chain `tip`, and `reorgs`.

`tip.block_height` is the height committed for the event type you just read, not a global number. Each decoded type runs its own decoder, so two reads can report different tips at once. `/v1/index/blocks` and `/v1/index/transactions` stay on the ingest tip (`source_block_height`). Re-read the tip per response.

Built on [Streams](/docs/streams): the decoder on your instance reads the same raw firehose you can.

Long-poll instead of tight-loop polling: `/v1/index/events` and `/v1/index/blocks` take `wait` (seconds, max 25). An empty page holds the connection open until new data commits or `wait` elapses; a page with rows answers at once.

```
GET /v1/index/events?event_type=ft_transfer&cursor=<last>&wait=25
```

An instance from before `wait` shipped answers `400`; fall back to a plain poll loop.

From the CLI:

```bash
secondlayer index transactions get 0x<tx_id>
secondlayer index mempool --contract-id SP….token
```

Tool names for agents are on [MCP and skills](/docs/mcp); see the [CLI](/docs/cli) for the rest. Mempool, state writes, PoX-5, sBTC and Runes have no MCP tool; use REST or the SDK. To be pushed instead of pulling: [Webhooks](/docs/webhooks).

</details>

<details id="print-schemas">
<summary>Print schemas</summary>

Clarity ABIs don't describe `print` payloads, and the shape varies **per topic** within one contract.

```bash
curl "$SECONDLAYER_API_URL/v1/index/contracts/SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-registry/print-schema" \
  -H "Authorization: Bearer $SECONDLAYER_API_KEY"
```

The response shape is in the [API reference](/docs/api-reference#get-print-schema). Sampled from indexed prints, raw Clarity hex deserialized for exact types, unified per topic. `camel_name` is what a handler sees on `event.data`.

- Optional fields report an `optional_some_rate`.
- Payloads with no `topic` string, or that aren't tuples, land under the `"*"` pseudo-topic with `non_tuple` set.
- Cached five minutes (`max-age=300` + weak `ETag`).

Backs `secondlayer subgraphs create <name> --from-contract <contract_id>`; see [Subgraphs](/docs/subgraphs#typed-print-payloads).

</details>

<details id="find-contracts-by-standard">
<summary>Find contracts by standard</summary>

Find every contract that conforms to a token standard, without keeping a list of addresses. A contract counts as **declared** when its source has `(impl-trait …)`, and **inferred** when its ABI matches the standard's shape.

```bash
curl -G "$SECONDLAYER_API_URL/v1/contracts" \
  -H "Authorization: Bearer $SECONDLAYER_API_KEY" \
  -d "trait=sip-010" -d "conformance=any"
```

```json
{
  "contracts": [
    {
      "contract_id": "SP3K8BC0PPEVCV7NZ6QSRWPQ2JE9E5B6N3PA0KBR9.usda-token",
      "deployer": "SP3K8BC0PPEVCV7NZ6QSRWPQ2JE9E5B6N3PA0KBR9",
      "block_height": 21000,
      "declared_traits": ["sip-010"],
      "inferred_standards": ["sip-010"],
      "abi_status": "fetched"
    }
  ],
  "next_cursor": "SP3K8BC0PPEVCV7NZ6QSRWPQ2JE9E5B6N3PA0KBR9.usda-token"
}
```

| Param | Description |
| --- | --- |
| `trait` | `sip-009`, `sip-010`, or `sip-013`. Required. |
| `conformance` | `declared`, `inferred`, or `any` (default). |
| `limit` | 1 to 500, default 100. |
| `cursor` | The previous `next_cursor`; `null` on the last page. |
| `include` | `abi` adds each contract's ABI. |

`GET /v1/contracts/{contract_id}` returns one contract. `trait` also filters the event and contract-call feeds, and a subgraph source can target a trait and pick up contracts deployed later: [Index by standard](/docs/subgraphs#index-by-standard-not-by-address).

</details>

<details id="state-writes">
<summary>State writes</summary>

The exact contract-state writes each canonical block committed, in node order. Use it to see which key a transaction changed, which events alone don't show.

```ts
const { state_writes, next_cursor } = await sl.index.stateWrites.list({
  blockHeight: 8054704,
  contractId: "SP1.vault", // only keys under this contract
  txContext: true, // join the writing transaction
});

for await (const w of sl.index.stateWrites.walk({ fromHeight: 8_000_000 })) {
  console.log(w.cursor, w.key, w.value_hex);
}
```

```bash
curl "$SECONDLAYER_API_URL/v1/index/state-writes?block_height=8054704" \
  -H "Authorization: Bearer $SECONDLAYER_API_KEY"
```

A row is `{ cursor, block_height, ordinal, tx_index, key, value_hex }`: `key` is the chain's storage key, `value_hex` the new value, and `tx_index` is `null` for block-level writes. The cursor is `<block_height>:<ordinal>`. `block_height` reads one block and excludes `from_height`/`to_height`.

Rows exist only from the height your node first sent the `state_writes` observer key. There is no earlier history. On your own box the key needs a node build that emits state writes, not yet the stock node. Rows bill like event rows.

</details>

## Decoded protocols

Index on contracts everyone shares, with the same verbs and envelope as every other feed. Not products of their own: your contract stays in `consume()` or a [subgraph](/docs/subgraphs).

<details id="pox-5">
<summary>PoX-5</summary>

Decoded prints from the `pox-5` boot contract (SIP-045, live since Bitcoin block 960,230), plus per-cycle totals. The print log, not a position scoreboard: positions and payouts are a subgraph you deploy.

| Read | Route | SDK |
| --- | --- | --- |
| All 19 print topics | `/v1/index/pox5/events` | `pox5.events.list` / `walk` / `consume` |
| Reward cycles of the current PoX | `/v1/index/pox/cycles` · `/{reward_cycle}` | `pox.cycles.list` / `walk` / `get` |
| PoX-4 stacking actions (historical) | `/v1/index/stacking` | `stacking.list` / `walk` |

```ts
for await (const e of sl.index.pox5.events.walk({ topic: "stake", signer: "SP…" })) {
  console.log(e.block_height, e.staker, e.amount_ustx);
}

const { events } = await sl.index.pox5.events.list({
  topic: "register-for-bond",
  fields: ["bond_index", "amount_sats"], // narrow the row to the columns you ask for
});
```

Event filters: `topic`, `staker`, `signer`, `signerManager`, `bondIndex`, `rewardCycle`, `fromHeight`, `toHeight`, `confirmed`. `signer` alone returns a pool's full activity, claims and key grants included. `register-for-bond` rows carry `bond_index`, `amount_sats`, `is_l1_lock` and `data.btc-lockup`. `confirmed=true` holds a read to rows past the reorg margin.

`pox5.events.consume()` is the checkpointed sweep, with the same options as [Build your index on it](#build-your-index-on-it). Cycles are exact to the node and follow the chain again at the next PoX fork. PoX-4 cycle history is final and not served; rebuild it from `/v1/index/stacking` on a self-hosted instance.

</details>

<details id="sbtc">
<summary>sBTC</summary>

The peg lifecycle, decoded, plus Bitcoin confirmation of sweeps. A `withdrawal-accept` only means the signers committed to a sweep, so your instance checks `sweep_txid` against bitcoind (the bundled full-node profile or an external `BITCOIN_RPC`). Deposits need no check: `completed-deposit` fires after the signers see the confirmations.

| Read | Route | SDK |
| --- | --- | --- |
| Raw peg log, six topics | `/v1/index/sbtc/events` | `sbtc.events.list` / `walk` / `consume` |
| Completed deposits | `/v1/index/sbtc/deposits` · `/{bitcoin_txid}` | `sbtc.deposits.list` / `walk` / `consume` |
| Withdrawal lifecycles | `/v1/index/sbtc/withdrawals` · `/{request_id}` | `sbtc.withdrawals.list` / `walk` / `get` |
| Totals | `/v1/index/sbtc/summary` | none |

A withdrawal carries a `settlement` object:

```json
{
  "request_id": 42,
  "status": "ACCEPTED",
  "settlement": { "sweep_txid": "abcd…", "btc_confirmations": 7, "settlement_confirmed": true, "btc_block_height": 880321, "confirmed_at": "2026-06-01T00:00:00.000Z" }
}
```

`settlement_confirmed` is `true` past the confirmation threshold, `false` while shallow, `null` when no sweep is observed yet (not a denial). The list takes it as a filter: `?settlement_confirmed=true` is confirmed peg-outs, `false` is the whole not-done bucket.

<Callout type="note" title="Withdrawals have no consume">

A withdrawal row mutates as it moves REQUESTED, ACCEPTED, settled, and a checkpoint only moves forward. Mirror the append-only `events` and derive status from the `withdrawal-*` topics; read `withdrawals.get(id)` for the assembled lifecycle.

</Callout>

Settlement is verified against your instance's bitcoind, not a custody guarantee: a signer set still controls the pegged UTXO. A Bitcoin reorg that un-confirms a sweep self-corrects on read. To be pushed: [Webhooks](/docs/webhooks#triggers).

</details>

<details id="runes">
<summary>Runes</summary>

A catalog of etched runes, a per-rune activity log, and balances, on a Bitcoin tip instead of a Stacks one. A rune's id is `<block>:<tx>` of its etch (`840000:3`). Its name is a unique A-Z string; spacers (`•`) are display only, so `DOG•GO•TO•THE•MOON`, `dog.go.to.the.moon` and `doggotothemoon` are one rune. Every `rune` field takes a `RuneRef`: an id or a name in any of those forms.

<Callout type="note" title="Self-host today, hosted follows">

Self-host with the `bitcoin` compose profile has Runes data now. Hosted answers `notes: "Runes data is not configured on this instance"` until it lands there.

</Callout>

| Read | Route | SDK |
| --- | --- | --- |
| Catalog | `/v1/index/runes` | `runes.list({ search, sort })` |
| One rune | `/v1/index/runes/{rune}` | `runes.get(ref)`, `null` on 404 |
| Current per-outpoint balances | `/v1/index/runes/balances` | `runes.balances({ address })` |
| Etch, mint, transfer, burn log | `/v1/index/runes/activity` | `runes.activity.list` / `walk` |

From the terminal: `secondlayer index runes [--search <prefix>] [--sort number|mints]`, `runes get <rune>`, `runes balances --address <addr>` (or `--outpoint <txid:vout>`), and `runes activity [--rune] [--address] [--kind etch,mint,transfer,burn] [--txid]`.

```ts
await sl.index.runes.list({ search: "dog", sort: "mints" });
await sl.index.runes.balances({ address: "bc1phnp234rd5hel0h8ulqvnq3zrww2td0a8q48hjcg7mv67j97jnxfq9ayczm" });

for await (const e of sl.index.runes.activity.walk({ rune: "840000:3" })) {
  console.log(e.kind, e.rune.spaced_name, e.amount);
}
```

`search` prefix-matches the name and `sort` is etch order or busiest-first (`mints`). `balances` needs exactly one of `address` or `outpoint`, enforced by the types; `rune` narrows either. Activity filters: `rune`, `address`, `kind`, `txid`; its cursor is `<block_height>:<event_index>`. Amounts (`premine`, `supply`, `burned`, `mints`) are u128 decimal strings, never `Number()` them. `supply` is `premine + mints × terms.amount`. Txids come back without `0x`.

A Bitcoin block needs 6 confirmations to count as final: `tip.finalized_height` is `tip.block_height - 6`. The catalog and balances read reorg-corrected snapshots, so their `reorgs` is always empty. Only `activity` is an append-only log, so only its `reorgs` can name replaced heights, at block level. The raw per-transaction events are on [Streams](/docs/streams#bitcoin-events-runes) with `chain=bitcoin`.

</details>
