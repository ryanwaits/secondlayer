# Webhooks

A signed POST to a URL you run, whenever a row you care about is written or a chain event you named happens.

<Callout type="note" title="Renamed from Subscriptions">

The product name is Webhooks: `secondlayer webhooks`, `sl.webhooks`, `webhooks_*`, and `/api/webhooks`. The old `subscriptions` names are gone. Tables were renamed in place on [upgrade](/docs/self-host/upgrade); rows stay. Test-ping bodies send `webhook_id`.

</Callout>

## Hosted vs self-host

Chain webhooks (triggers on raw events — no subgraph deployed) run either way. Subgraph webhooks (triggers on a subgraph table you deployed) are self-host only until subgraphs themselves go hosted.

| | Self-host | Hosted (`api.secondlayer.tools`) |
| --- | --- | --- |
| Chain webhooks | Yes | Yes — an `sk-sl_*` key and prepaid credits, no instance to run |
| Subgraph webhooks | Yes | Not yet |
| Auth | `INSTANCE_TOKEN`, your own instance | `sk-sl_*` account key |
| `max_retries` | Any value you set | Capped at 7 |
| `timeout_ms` | Any value you set | Capped at 30000 |
| Rate limits | None (it's your box) | Per account: create/update/delete 30/min, `test` 10/min, `replay` 5/hour, reads 600/min |
| Egress | Whatever your network allows | Your webhook receiver + our own read APIs only — a tenant's compose network can't reach another tenant or our internal services |
| Pricing | Free (self-host) | `webhook.event` per delivered event; retries are never billed |
| Isolation | N/A (you run it) | One full self-host stack per account, not a shared multi-tenant runtime — your data never shares a database or process with anyone else's |

A hosted chain webhook works exactly like a self-host one from the CLI/SDK: set `SECONDLAYER_API_KEY` (`sk-sl_*`) and point at `api.secondlayer.tools` (or leave the default). Delivery semantics — at-least-once, unordered, reorg rollback — are identical on both: [Receiving deliveries](/docs/webhooks/deliveries).

## In the dashboard

[`/account/webhooks`](/account/webhooks) lists a hosted account's webhooks and, per webhook, the last 100 delivery attempts, a diagnosis, and failed events waiting to be resent. From there you can send a test event, pause or resume, rotate the signing secret, resend a failed event (or all of them), and delete. Create and edit stay on the CLI/SDK — the dashboard never writes a webhook definition, only watches and fixes one.

## Create a webhook

```bash
secondlayer webhooks create sbtc-webhook \
  --no-scaffold \
  --subgraph sbtc-flows \
  --table transfers \
  --url https://your-app.com/webhooks/sbtc
```

Omit `--no-scaffold` to scaffold a local receiver (`-r inngest | trigger | cloudflare | node`) named after the webhook. What arrives and how to trust it: [Receiving deliveries](/docs/webhooks/deliveries).

## Row lifecycle verbs

A subgraph webhook tracks the whole life of each row. The payload `type` is `` `<subgraph>.<table>.<verb>` ``:

| Verb | Fires on | Example `type` |
| --- | --- | --- |
| `created` | row insert | `sbtc-flows.transfers.created` |
| `updated` | row update | `sbtc-flows.transfers.updated` |
| `deleted` | row delete | `sbtc-flows.transfers.deleted` |

## Two kinds

A subgraph webhook fires on rows your handler writes. A chain webhook fires on raw events, with no subgraph deployed.

- **`subgraph`**: `{ name, subgraphName, tableName, url, filter? }`.
- **`chain`**: `{ name, url, triggers: [...] }`. Starts at the chain tip, no backfill.

## Triggers

A chain webhook takes a `triggers` array (1–50) instead of `subgraphName`/`tableName`. Use the `trigger.*` factories or the equivalent raw objects.

```ts
import { trigger } from "@secondlayer/sdk";

await sl.webhooks.create({
  name: "amm-swaps",
  url: "https://my-app.com/webhook",
  triggers: [
    trigger.contractCall({ contractId: "SP....amm", functionName: "swap-*" }),
    trigger.ftTransfer({ trait: "sip-010", minAmount: "1000000" }),
  ],
});
```

`*` wildcards are allowed; `trait` scopes to a SIP/trait.

| Builder | `type` | Fields |
| --- | --- | --- |
| `trigger.contractCall` | `contract_call` | `contractId`, `functionName`, `caller`, `trait` |
| `trigger.contractDeploy` | `contract_deploy` | `deployer`, `contractName` |
| `trigger.ftTransfer` | `ft_transfer` | `assetIdentifier`, `sender`, `recipient`, `minAmount`, `trait` |
| `trigger.ftMint` | `ft_mint` | `assetIdentifier`, `recipient`, `minAmount`, `trait` |
| `trigger.ftBurn` | `ft_burn` | `assetIdentifier`, `sender`, `minAmount`, `trait` |
| `trigger.nftTransfer` | `nft_transfer` | `assetIdentifier`, `sender`, `recipient`, `trait` |
| `trigger.nftMint` | `nft_mint` | `assetIdentifier`, `recipient`, `trait` |
| `trigger.nftBurn` | `nft_burn` | `assetIdentifier`, `sender`, `trait` |
| `trigger.stxTransfer` | `stx_transfer` | `sender`, `recipient`, `minAmount`, `maxAmount` |
| `trigger.stxMint` | `stx_mint` | `recipient`, `minAmount` |
| `trigger.stxBurn` | `stx_burn` | `sender`, `minAmount` |
| `trigger.stxLock` | `stx_lock` | `lockedAddress`, `minAmount` |
| `trigger.printEvent` | `print_event` | `contractId`, `topic`, `trait` |

Validation is strict per type: mints take `recipient` (no `sender`), burns take `sender` (no `recipient`); any field outside a type's set is rejected with a 400.

Five sBTC peg triggers (`sbtcDeposit`, `sbtcWithdrawalCreate`, `sbtcWithdrawalAccept`, `sbtcWithdrawalReject`, `sbtcWithdrawalSweptConfirmed`) track the [sBTC settlement](/docs/sbtc-settlement) lifecycle.

`POST /api/webhooks` accepts the same array. From the CLI, pass `--trigger` (repeatable, one JSON object each) or `--triggers-file` (a JSON array) instead of `--subgraph`/`--table`:

```bash
secondlayer webhooks create amm-swaps \
  --url https://my-app.com/webhook \
  --trigger '{"type":"contract_call","contractId":"SP....amm","functionName":"swap-*"}' \
  --trigger '{"type":"sbtc_deposit"}'
```

`--trigger`/`--triggers-file` switches `create` into chain mode, with no subgraph and no scaffold. Each trigger is validated before provisioning; the signing secret prints once.

## Replay

Re-deliver historical rows over an existing webhook.

```ts
const { replayId, enqueuedCount, scannedCount } = await sl.webhooks.replay(id, {
  fromBlock: 8000000,
  toBlock: 8050000,
});
```

Replays are **idempotent**, **historical only**, and **never move the live cursor**. The range is capped at **100,000 blocks**. Both kinds are flagged `is_replay`.

| Webhook kind | Replay delivers as |
| --- | --- |
| Subgraph | `<subgraph>.<table>.replay`, a distinct verb (not the live `.created`/`.updated`/`.deleted` types) |
| Chain | The standard `chain.{type}.apply` envelope |

`sbtc_withdrawal_swept_confirmed` fires on a Bitcoin confirmation rather than a Stacks block, so it is forward-only and never replayed. The CLI warns.

## Test delivery

`secondlayer webhooks test <idOrName> --post` sends a logged test delivery:

```json
{
  "type": "chain.test.apply",
  "timestamp": "2026-05-01T12:00:00.000Z",
  "data": {
    "test": true,
    "message": "Secondlayer test delivery",
    "webhook_id": "sub-…",
    "sent_at": "2026-05-01T12:00:00.000Z"
  }
}
```

Not a real chain event, so check `data.test` before treating a delivery as live.

## Troubleshooting

`secondlayer webhooks doctor <idOrName>` and the dashboard's detail page run the same five rules against your last 100 delivery attempts. Every rule is deterministic: no model, and it only states what the numbers prove. Each fires on a fixed threshold, listed below, and each reports evidence you can check yourself.

### Receiver rate-limited

Fires when at least 10 of the last 100 attempts are `429`s, and `429`s are at least half that window. Your receiver is answering, but throttling us.

Lower `--concurrency` on the webhook, or make your receiver honor the `Retry-After` header it's sending back:

```bash
secondlayer webhooks update <idOrName> --concurrency 2
```

### Receiver down

Fires when the 5 most recent attempts are all `5xx` responses or got no response at all (timeout or connection failure). Check your receiver's health and logs, then confirm it's back with a test delivery:

```bash
secondlayer webhooks test <idOrName>
```

### Receiver rejects

Fires when the 5 most recent attempts are all `4xx` responses other than `429`. Your receiver is reachable and actively rejecting the request: check auth config or signature verification first.

```bash
secondlayer webhooks test <idOrName>
```

### Receiver slow

Fires when the median response time of the newest 20 attempts is at least half this webhook's `timeoutMs`. Speed up your receiver, or raise the timeout (capped at 30s hosted):

```bash
secondlayer webhooks update <idOrName> --timeout-ms 30000
```

### Delivery lag

Fires when the median gap between a block's time and when we dispatched its event, over the newest 20 attempts, exceeds 60 seconds. This is latency on our side, not your receiver: no action needed on your end.
